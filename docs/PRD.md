## 一、背景与目标

### 1.1 问题描述

当前翻唱一首歌，物料准备是 6 步纯手工：

1. 打开 Apple Music 搜索歌曲 A，复制歌曲链接
2. 把链接交给 Agent，由 Apple Music Downloader Skill 下载为 FLAC
3. 打开 Ultimate Vocal Remover（下称 UVR），手动导入 FLAC
4. 选模型 `melband_roformer_inst_v2`，分离出伴奏与人声
5. 把上一步的人声再导入一次，选模型 `mel_band_roformer_karaoke_aufr33_viperx_sdr_10.1956`，分离出主音与和声
6. 手动把 4~5 个产物、封面、歌词逐个搬进 `D:\Videos\<歌名>\`

实测痛点（依据现有成品目录 `D:\Videos\酒干倘卖无`、`D:\Videos\是否我真的一无所有`）：

| 痛点 | 具体表现 |
|---|---|
| 链路长且跨 4 个工具 | 浏览器 → Agent → Docker → UVR GUI → 资源管理器，任何一环分神就断 |
| Docker 平时关闭 | 每次要手动启动 Docker Desktop 并等它就绪，否则下载必然失败 |
| 文件语义丢失 | UVR 产出 `1_1_酒干倘卖无-苏芮_(Vocals)_(Instrumental).wav`，主音与和声只能靠记忆判断 |
| 命名混乱 | 同一目录里混着 `gasa.lrc.txt`（Tab 分隔、非标准 LRC）、`ld.wav`、`ld.pkf`、`未命名项目.wfpx` |
| 歌词要二次加工 | 拿到的是 Tab 分隔文本，字幕软件只认 LRC/SRT |
| 必须守着电脑 | 一张专辑十几首要逐首逐步点击 |
| 重来成本高 | 下错版本或想换模型，整个流程从第 1 步重跑 |

### 1.2 目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 把「我要唱 A」到「物料齐备可开录」的人工操作压缩到 2 步（输入歌名 → 选中版本） | 人工点击/输入 ≤ 2 次（首次配置除外） |
| G2 | 单曲物料准备的人工在电脑前时间 ≤ 2 分钟，其余为自动等待 | 秒表实测，10 首取中位数 |
| G3 | 产出的目录**零加工即可开录**：3 条分离轨命名自解释、起始于 0 秒、时长一致 | 抽 10 首，直接可用的比例 ≥ 90% |
| G4 | 支持夜间挂机批量：勾选后无人值守，次日物料齐备 | 10 首批量任务无人干预完成率 ≥ 90% |
| G5 | 重复准备同一首歌（换模型/补缺料）只执行缺失或指定的步骤 | 二次执行耗时 ≤ 首次的 40% |
| G6 | 进度条给出的剩余时间可信 | 样本 ≥ 5 次后，ETA 误差 ≤ ±30% |

> **性能关注点是 ETA 的可信度**：机器性能足够，耗时以实际为准；批量挂机时用户靠剩余时间决定是否离开电脑（见 FR-12）。

### 1.3 产品范围

本产品**只负责从选歌到物料落盘**这一段，具体范围如下：

| 维度 | 范围 |
|---|---|
| 流程 | 选歌 → 下载原曲 → 封面与元数据 → 歌词（含外语双语化）→ 两段分离 → 落盘 |
| 交付物 | 仅附录 B 所列 7 个文件 + 1 个隐藏状态文件 |
| 分离轨 | 仅伴奏、主音、和声三轨 |
| 音频处理 | 仅格式转换与分离；原曲与分离轨保持模型原始输出 |
| 双语歌词 | 仅为非中文语系歌词附加中文译文 |
| 界面 | 仅包含体检、搜歌、曲目清单、队列、任务详情、设置 |
| 内部记录 | 仅用于增量补齐、ETA 学习、队列恢复、「已备料」角标 |
| 磁盘访问 | 在 `D:\Videos` 下仅访问本工具创建、且含 `.ktvmeta.json` 的子目录，以及正在处理的曲目对应的目标路径 |
| 数据位置 | 仅保存在本机 |
| 内容来源 | 仅处理用户本人 Apple Music 订阅可访问的内容，账号与订阅由用户自备 |

录音、混音、母带、效果处理（去混响、降噪、去回声）、升降调与变速、视频合成与字幕压制、在线播放，均由用户在各自的专业软件中完成。

## 二、用户与场景

### 2.1 角色

| 角色 | 说明 |
|---|---|
| 唯一用户（本人） | 会操作 DAW 与 UVR，清楚自己要什么；接受技术型提示；失败时需要可诊断信息；**关心的是「还要等多久」** |

### 2.2 核心场景

**场景 A：单曲即时准备（最高频）**
> 晚上想唱《是否我真的一无所有》。打开工具，输入歌名，候选列表里选「王杰 - 是否我真的一无所有（1990 / 4:12）」。目录里 7 个文件齐备，点「打开文件夹」，把 3 条 WAV 拖进 Audacity 开录。

**场景 B：整张专辑挂机备料**
> 周五晚上想周末连着录几张专辑。贴一张专辑链接，工具列出 12 首曲目（含时长、是否已备过），勾选 9 首，点开始。界面显示「预计剩余 1 小时 42 分」。关掉屏幕睡觉。次日早上收到「9 首完成，2 首歌词未获取」的通知。

**场景 C：换模型重做伴奏**
> 觉得某首伴奏分离有残留。在任务详情点「重跑分离」，只重跑 pass1/pass2，下载与歌词结果直接复用。

**场景 D：外文歌**
> 想唱一首德语音乐剧选段。工具检出歌词语言为非中文语系，自动逐句翻译，产出双语 LRC 与 SRT，时间轴与原唱一致。

## 三、核心概念与术语

| 术语 | 定义 |
|---|---|
| **pass1** | 第一次分离：原曲 → `melband_roformer_inst_v2` → 伴奏 + 完整人声 |
| **pass2** | 第二次分离：pass1 的完整人声 → `mel_band_roformer_karaoke_aufr33_viperx_sdr_10.1956` → 主音 + 和声 |
| **伴奏** | 去掉全部人声的器乐轨（pass1 的 Instrumental 输出） |
| **主音** | 领唱人声（pass2 的 Vocals 输出） |
| **和声** | 伴唱/和声部（pass2 的 Instrumental 输出） |
| **完整人声** | pass1 的 Vocals 输出 = 主音 + 和声。仅作为 pass2 输入与重跑中间件，保存在工作目录 |
| **物料** | 本产品交付物集合：原曲、伴奏、主音、和声、封面、歌词（LRC/SRT） |
| **曲目（Track）** | 一次 Apple Music 单曲记录，以 Apple 的 `trackId` 为唯一键 |
| **任务（Job）** | 一次「为某曲目准备物料」的执行实例，可重复执行 |

> ⚠️ **模型输出语义容易搞反**，实现时只按附录 A 映射表执行。

## 四、功能需求

### FR-01 环境体检与 Docker 自动关联启动

**描述**：应用启动时检查全部外部依赖；Docker Desktop 这类平时关闭的依赖由应用负责拉起。

**规则**

1. 应用启动时自动执行 9 项体检，结果呈现在顶部体检面板
2. **Docker Desktop 自动关联启动**：
   - 检测到 Docker 守护进程不可用时，直接拉起 `Docker Desktop.exe`（路径可配置）
   - 拉起后轮询守护进程就绪，超时 120 秒；超时则展示「Docker 启动失败」并提供「重新拉起」「查看日志」
   - 拉起过程显示「正在启动 Docker（预计 30~60 秒）」，这段时间在界面上单独呈现为环境等待
3. Docker 就绪后自动检查 Wrapper 容器，未运行则自动 `compose up`
4. 所有路径（Docker Desktop、Wrapper 目录、GPAC、ffmpeg、模型文件、输出根目录）均可配置且参与体检

| 检查项 | 不满足时的行为 |
|---|---|
| Docker Desktop 守护进程可连接 | **自动拉起** + 轮询就绪 + 进度提示 |
| Wrapper 解密容器运行中 | 显示状态 + 自动 `compose up` + 「重试」 |
| Wrapper 端口 10020 / 20020 可连通 | 显示具体端口与错误 |
| Wrapper 登录态有效 | 「需重新登录」→ 进入 FR-02 |
| GPAC（MP4Box）可执行 | 显示配置路径入口 |
| ffmpeg 可执行 | 同上 |
| 分离工具可执行，分离模型文件存在（2 个 `.ckpt` + 对应 yaml） | 显示缺失项与期望路径 |
| 输出根目录 `D:\Videos` 可写 | 只读时禁止启动任务 |
| 剩余磁盘空间 | < 5 GB 警告；< 1 GB 禁止启动新任务 |

**验收标准**

1. 冷机状态下（Docker 未启动）双击启动应用，全程由应用拉起 Docker Desktop
2. 9 项检查在 10 秒内全部返回结果（Docker 启动等待除外），界面先打开、检查结果陆续呈现
3. 每项失败都给出「哪个路径 / 哪个端口 / 哪条命令」级别的定位信息
4. Docker 从冷启动到可用的总耗时在界面可见，并且只显示为环境等待
5. 应用退出时，Docker 保持原有运行状态

### FR-02 Apple Music 登录与 2FA

**规则**

1. 账号密码仅以 Windows DPAPI 密文存储在本地
2. 检测到等待 2FA 时，界面弹 6 位数字输入框，提交后由程序写入容器内部
3. 写入后 60 秒内未成功，提示「验证码已过期，重新发起」
4. 登录态缓存成功后，后续启动直接使用缓存，直到 token 失效

**验收标准**

1. 从弹出输入框到登录成功 ≤ 30 秒（人工输入时间除外）
2. token 失效时明确提示「需重新登录 Apple ID」，与下载失败区分显示
3. 密码在日志、界面、错误提示中只以脱敏形式出现

### FR-03 搜歌与版本确认（US-01）

> **US-01** 作为用户，我输入歌名后要能一眼选中正确版本，避免下错 Live 版 / 翻唱版。

**输入支持**

1. 歌名关键词（中/英/德/日等任意语言）
2. 直接粘贴 Apple Music 链接（单曲、专辑、歌单）
3. 单曲链接可直接跳过候选列表，直达下载

**候选列表规则**

| 字段 | 要求 |
|---|---|
| 必显示 | 歌曲名、歌手、专辑、时长、发行年份 |
| 版本标识 | 曲名含 Live / Remix / Acoustic / Instrumental / Demo 等关键词时用标签高亮 |
| 排序 | 精确匹配优先 → 热度优先 |
| 数量 | 默认 10 条，可「加载更多」 |
| 已备料标记 | 该 `trackId` 已有记录时显示「已备料」角标，点击可直接打开目录 |

**验收标准**

1. 输入歌名后 3 秒内出候选
2. 同名不同版本可通过「歌手 + 专辑 + 时长」三者区分，每一行唯一
3. 命中 0 条时提示「未找到，建议改用『歌手 + 歌名』重搜」或「直接粘贴链接」
4. 繁体、简体输入均可命中同一曲目
5. 「已备料」判定仅依据内部记录与 `.ktvmeta.json`

---

### FR-04 音频下载

**规则**

1. 目标格式：**FLAC 无损**，保持原采样率/位深
2. 下载链路产出 ALAC（`.m4a`）时，自动无损转为 FLAC
3. 下载产物先落在临时目录，校验通过后才进入正式目录
4. 下载并发固定为 **1**
5. 下载失败自动重试 1 次；仍失败则整首标记失败并记录原因

**验收标准**

1. 下载完成的 FLAC 可被 ffprobe 正常解析，时长与 Apple Music 元数据一致（误差 ≤ 1 秒）
2. 文件大小 > 0 且可完整解码
3. 下载失败时能区分三类原因：Docker 未就绪 / 账号或 token 问题 / 该曲目不可获取
4. 已存在曲名对应的 FLAC，或 `.ktvmeta.json` 记录的原曲文件时跳过下载（用户点「强制重跑」时重新下载）。外部目录里若只有一个 FLAC，把它当作原曲，不改名、不覆盖
5. 原曲采样率/位深在界面可见（用于确认是否拿到 Hi-Res）

---

### FR-05 封面与元数据

**规则**

1. 封面取 Apple 提供的最高分辨率（3000×3000），存为 `封面.jpg`
2. 最高分辨率不可得时降级取可用最大值，并在详情页注明实际尺寸
3. 曲名 FLAC 写入元数据：歌名、歌手、专辑、专辑艺人、音轨号、碟号、年份、封面内嵌
4. 元数据仅写入该 FLAC；伴奏/主音/和声保持分离输出原样（保证 DAW 兼容）

**验收标准**

1. `封面.jpg` 可正常打开，宽高相等，短边 ≥ 1000
2. 用播放器打开曲名 FLAC 能显示封面与曲名歌手
3. 封面获取失败时，其他物料照常产出，仅该项标红

### FR-06 歌词获取与格式化（US-02）

> **US-02** 作为用户，我要一份时间轴准确、句子与原唱一致的 LRC 和 SRT，边唱边看不串行。

**规则**

1. 歌词来源：Apple Music 官方歌词（带时间轴）
2. **逐句原样保留**：句子划分、文字、繁简形态均与 Apple 原文一致，**括号内的和声/伴唱行同样保留**
3. 输出 `歌词.lrc`（标准 LRC，行级时间轴）+ `歌词.srt`
4. 时间轴以原曲音频为准（与曲名 FLAC 同源，天然对齐）
5. 仅有纯文本、无时间轴时：仍输出 LRC/SRT，时间戳统一置 0，界面标黄「无时间轴」
6. 歌词完全不可得时：跳过歌词文件，标红「无歌词」

**验收标准**

1. LRC 可被主流播放器识别，逐行进字与音频播放位置偏差 ≤ 0.3 秒
2. SRT 可被播放器/剪辑软件导入，句子数与原歌词句数一致
3. 括号和声行保留（例：`(酒矸倘賣無)`）
4. 繁体保持繁体，简体保持简体

---

### FR-07 外语歌词双语化（US-03）

> **US-03** 作为用户，唱非中文歌时我要看到逐句译文，且译文与原文严格同时间轴。

**触发条件**

1. Apple 歌词语言标签以 `zh` 开头（含 `zh-Hans` / `zh-Hant` / 粤语）→ **中文语系，仅输出原文**
2. 配置页「自动翻译歌词」打开，且这首歌没有单独关掉时，其余语言（英语、德语、日语、韩语、法语、西班牙语等）→ **触发翻译**
3. 语言标签缺失时，按「CJK 汉字占非空白字符比例」判定：≥ 30% 视为中文语系
4. 任务详情可以单独打开或关闭这首的翻译。单独选择优先于配置开关。中文语系无论开关如何都只输出原文
5. 关掉翻译后重跑歌词，输出单语版；再次打开时复用已缓存译文

**翻译规则**

1. 走 **OpenAI 兼容接口**：base_url、model、key 三项均可在配置页填写并「测试连接」，默认按 DeepSeek 系模型预置
2. 逐句翻译，**N 句原文严格对应 N 句译文**，一一对应
3. 译文保留原文行内标点与语气，口语化表达，只输出译文本身
4. 翻译失败或返回句数不匹配时：输出**单语版**歌词 + 标红「双语失败」
5. 翻译结果缓存到曲目元数据，重跑歌词步骤时复用，避免重复计费
6. 单次翻译最多重试 1 次；超时 30 秒视为失败
7. 未配置 API key 时跳过翻译，输出单语版，并提示去配置页填写

**排版规则**

LRC — 同时间戳两行，原文在前：

```
[00:34.20]多麼熟悉的聲音
[00:34.20]多么熟悉的声音
[00:38.50]陪我多少年風和雨
[00:38.50]陪我多少年风和雨
```

SRT — 同一条字幕内两行：

```
12
00:00:34,200 --> 00:00:38,400
多麼熟悉的聲音
多么熟悉的声音
```

**验收标准**

1. 双语 LRC 中每个时间戳最多 2 行，总行数 = 句数 × 2
2. 双语 SRT 中每条 cue 内恰好 2 行文本
3. 原文行与单语版完全一致
4. 中文歌只输出原文行
5. 翻译 token 消耗在任务详情可见
6. 配置页「测试连接」失败时，能明确指认是 base_url、key 还是模型名的问题

### FR-08 两段分离（US-04）

> **US-04** 作为用户，我要的伴奏、主音、和声一次跑出来，且文件语义准确。

**模型（固定，配置文件中可覆盖）**

| 阶段 | 模型 | 输入 | 输出 → 落盘名 |
|---|---|---|---|
| pass1 | `melband_roformer_inst_v2` | `<曲名>.flac` | Instrumental → `伴奏.wav`；Vocals → **完整人声（工作目录中间件）** |
| pass2 | `mel_band_roformer_karaoke_aufr33_viperx_sdr_10.1956` | 完整人声 | Vocals → `主音.wav`；Instrumental → `和声.wav` |

**规则**

1. **输出格式固定**：WAV，**44100 Hz / 16 bit / 立体声**，与用户 DAW 的工作规格一致
2. 原曲 FLAC 保持原始采样率与位深（原曲是存档，分离轨是工作文件）
3. 分离轨保持模型原始输出，仅做格式封装
4. **和声轨总是生成**
5. 完整人声保留到整首进入 `完成` 状态后删除，以支持仅重跑 pass2
6. 分离并发数**可配置，默认 2，上限 2**
7. 同一首曲目内 pass1 → pass2 严格串行
8. 分离失败时保留中间文件，支持「只重跑分离」

**验收标准**

1. 三个 stem 时长与原曲一致（误差 ≤ 0.05 秒）
2. `伴奏.wav` 为纯器乐；`主音.wav` 可听清领唱；`和声.wav` 为伴唱成分
3. 三个 WAV 的采样率 = 44100 Hz、位深 = 16 bit、声道 = 2（ffprobe 校验，仅接受此规格）
4. 并发设为 2 时，任意时刻运行中的分离进程 ≤ 2
5. 意外中断后重启应用，可续跑未完成的分离步骤

### FR-09 输出目录与命名（US-05）

> **US-05** 作为用户，我打开文件夹就知道每个文件是什么。

**目录结构**

```
D:\Videos\<歌名>\
├── <曲名>.flac        ← 原曲，文件名就是曲名，不使用固定名「原曲.flac」
├── 伴奏.wav
├── 主音.wav
├── 和声.wav
├── 封面.jpg
├── 歌词.lrc
├── 歌词.srt
└── .ktvmeta.json      ← 内部状态文件（隐藏，属于工具内部数据）
```

原曲文件名与目录名使用同一套净化规则。目录因重名写成 `<曲名> (歌手)` 时，原曲文件仍用曲名。实际文件名写入 `.ktvmeta.json` 的 `originalFile`。

**目录名规则**

1. 默认取 Apple Music 曲名原文，保留原语言与繁体/简体形态
2. 非法字符 `\ / : * ? " < > |` 替换为全角对应字符
3. 去掉首尾空格与结尾点号
4. 截断到 80 字符（超长用 `…` 结尾）
5. 同名目录已存在且 `.ktvmeta.json` 中 `trackId` **不同** → 追加 ` (歌手)`
6. 仍冲突 → 追加 ` (2)`、` (3)`

**`.ktvmeta.json` 必含字段**

`trackId`、`曲名`、`歌手`、`专辑`、`年份`、`时长`、`原曲采样率/位深`、`歌词语言`、`是否双语`、`各阶段状态与耗时`、`模型版本`、`创建时间`、`最近执行时间`、`最后一次错误`

**验收标准**

1. 按上述 6 条规则生成目录名，含 `/`、`:`、超长名的曲目均能正确落盘（路径总长 < 260）
2. 交付物仅为 7 个文件 + 1 个隐藏状态文件：原曲名为曲名，其余 6 个文件名与上方结构完全一致
3. 同一首歌二次执行命中同一目录
4. 目录中已有的用户文件（录音、工程文件、素材）在任何操作下都保持原样

### FR-10 重跑与增量补齐

**规则**

1. 每次执行先读 `.ktvmeta.json`，逐阶段判断「已完成 / 待执行 / 失败」
2. 已完成且产物存在、大小 > 0 → 跳过
3. 支持 **整首重跑** / **单步重跑**（下载、封面、歌词、pass1、pass2）
4. 重跑覆盖同名文件前，先把旧文件移到 `_backup_<时间戳>\` 子目录
5. 目录存在但无 `.ktvmeta.json`（如现有手工目录）→ 视为「外部目录」，仅补缺失文件，已有同名文件保持原样
6. 判定「是否已备料」仅依据内部记录与 `.ktvmeta.json`

**验收标准**

1. 二次执行时已完成阶段耗时接近 0
2. 单步重跑只影响该步骤及其下游产物
3. 现有手工目录 `D:\Videos\酒干倘卖无` 被接入时，原有 `.aup3`、`.mp4`、`.png` 等文件保持原样

### FR-11 批量与队列（US-06）

> **US-06** 作为用户，我要贴一张专辑链接后勾选曲目，然后去睡觉。

**规则**

1. 支持专辑链接、歌单链接、多行歌名批量导入
2. 解析后先出**曲目清单**：序号、曲名、时长、已备料状态、预计体积、勾选框
3. 默认勾选「未备料」曲目
4. 确认后进入队列，FIFO 执行
5. 队列状态：`排队中 / 执行中 / 完成 / 部分完成 / 失败 / 已取消 / 已中断`
6. 支持单条取消、全部暂停、全部继续
7. 队列**持久化**：应用重启、电脑重启后恢复并续跑
8. 队列全部结束触发一次通知（桌面通知 + 提示音），部分失败时带上失败数量
9. 队列顶部显示**整体剩余时间**（基于 FR-12 的 ETA 汇总）
10. 单次勾选上限 50 首，超出时提示分批

**验收标准**

1. 12 首专辑清单解析 ≤ 5 秒，曲目数量与专辑页一致
2. 批量执行时同时运行的分离进程数 ≤ 配置上限
3. 中途关闭应用，重启后未完成曲目继续执行，已完成的直接跳过
4. 通知能区分「全部成功」与「N 首部分完成 / M 首失败」
5. 整体剩余时间随进度单调收敛

### FR-12 进度、ETA 自学习与失败诊断（US-07）

> **US-07** 作为用户，挂机前我要知道「还要等多久」。

**A. 进度展示**

1. 每首曲目显示 5 个阶段与耗时：下载 / 封面 / 歌词 / 分离 pass1 / 分离 pass2
2. 显示阶段内进度与整体进度
3. 批量时显示队列整体进度（已完/总数 + 整体 ETA）

**B. ETA 预估（按历史自学习）**

1. 记录每次执行的实际耗时样本，供后续预估使用
2. **样本结构**：`阶段 × 模型 × 音频物理时长 → 实际耗时`
3. **单位耗时系数** = `实际耗时 / 音频时长（秒）`，按阶段分别统计；pass1 与 pass2 模型不同，系数独立
4. **取数策略**：取该阶段最近 **10 次**样本的单位耗时**中位数**（抗离群值）；样本 < 3 次时用内置默认系数。pass1 默认 `0.24`，pass2 默认 `0.28`（RTX 5070 Ti 上 354.947 秒曲目的实测单位耗时，向上取到两位小数）
5. **预估公式**：`预计耗时 = 本曲音频时长 × 单位耗时系数`
6. **不确定性表达**：
   - 样本 ≥ 5 且离散度小 → 单值「预计剩余 2 分 30 秒」
   - 样本不足或离散度大 → 区间「预计剩余 3~7 分钟」
   - 冷启动（0 样本）→ 「首次执行，暂用默认估算」
7. ETA 在每个阶段结束、每首歌完成时重算；**每次都回写真实耗时**，形成学习闭环
8. 下载阶段按文件大小与当前速率估算；歌词/翻译阶段按句数与历史吞吐估算

**C. 分离阶段进度条的诚实约束**

1. 分离进度能读到 tqdm 百分比，以真实进度为准。已在一首 354.947 秒的曲目上确认两段分离都走到 100
2. 读不到真实进度时，进度条为**基于 ETA 的时间插值**（平滑推进），并标注「估算进度」

**D. 失败诊断**

1. 失败时展示：失败阶段、原始错误摘要、可执行建议（例：「Docker 未启动，点此启动」）
2. 支持复制完整错误日志
3. **部分完成策略**：能交多少交多少，缺的标红列出，目录照建

**验收标准**

1. 任一失败都能定位到具体阶段和具体原因
2. 部分完成状态下明确列出「缺：歌词、和声」这类清单
3. 进度更新延迟 ≤ 3 秒
4. 累计 5 首样本后，单曲 ETA 误差 ≤ ±30%
5. 界面能同时看到「本次预估值」与「完成后实际值」
6. 插入一条异常慢样本（如慢 3 倍）后，后续 ETA 保持稳定（中位数抗离群）

### FR-13 交付后的衔接

**背景**：用户的实际操作是「打开文件夹 → 把音频拖进 Audacity」，因此 P0 只提供文件夹入口。

**P0 规则**

**背景**：`D:\Videos` 里还有用户的其他项目，本产品仅保留支撑增量补齐、ETA 学习、队列恢复所需的最小本地记录。

## 五、主流程与状态机

### 5.1 主流程（单曲）

```
1. 启动应用 → 体检 → Docker 不可用时自动拉起 Desktop 并等就绪
2. 输入歌名 / 粘贴链接
3. 候选列表 → 选中一条（含 trackId）
4. 创建或复用目录
5. 下载原曲 FLAC → 校验（ffprobe 可解析、时长匹配、记录采样率）
6. 取封面 + 写元数据
7. 取歌词 → 语言判定 →（非中文）逐句翻译
8. pass1：原曲 → 伴奏 + 完整人声
9. pass2：完整人声 → 主音 + 和声
10. 落盘校验（6 个物料齐全、时长一致、WAV 规格 = 44.1k/16bit/2ch）
11. 回写实际耗时（ETA 学习）→ 状态置完成/部分完成 → 通知
```

### 5.2 状态机

| 当前状态 | 触发动作 | 目标状态 | 副作用 |
|---|---|---|---|
| — | 用户选中曲目 | 排队中 | 写入任务记录 |
| 排队中 | 调度器取任务 | 执行中 | 占用并发槽位 |
| 执行中 | 全部阶段成功 | 完成 | 写 `.ktvmeta.json`、回写耗时、发通知 |
| 执行中 | 仅封面/歌词失败 | 部分完成 | 缺失项标红、回写耗时、发通知 |
| 执行中 | 关键阶段失败（下载/两个分离） | 失败 | 保留已得产物、记录错误 |
| 执行中 | 用户取消 | 已取消 | 终止当前阶段、保留中间文件 |
| 执行中 | 应用退出或崩溃 | 已中断 | 重启后自动回到排队中续跑 |
| 任何状态 | 整首重跑 | 排队中 | 依 `.ktvmeta.json` 跳过已完成 |
| 任何状态 | 单步重跑 | 排队中 | 仅执行该步骤及其下游 |

### 5.3 并发约束

| 资源 | 并发上限 | 原因 |
|---|---|---|
| Apple Music 下载 | 1 | 单容器、单账号，避免 token 与网络冲突 |
| 分离进程 | 可配置，默认 2，上限 2 | 分离进程能力上限 |
| 歌词翻译请求 | 可配 1~3，默认 1 | 避免 API 限流 |

> **技术可行性结论**：两个模型的 `.ckpt` 与 `.yaml` 都齐备，且都在 audio-separator 支持的 UVR 官方模型清单中，分离环节可通过命令行批量调用，挂机运行。

## 十、风险清单

| 编号 | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | Docker 冷启动慢（30~60 秒） | 首次任务看起来卡住 | 明确显示「正在启动 Docker」+ 独立进度，与任务状态分开 |
| R2 | Wrapper token 过期、2FA 超时 | 下载中断 | 状态明确区分「需登录」与「下载失败」 |
| R3 | 下载产物落在非预期位置 | 下载显示成功但目录为空 | 以落盘文件存在且可解码作为成功标准 |
| R4 | 分离阶段无真实进度可读 | 进度条失真 | 标注「估算进度」，用 ETA 时间插值 |
| R5 | ETA 冷启动不准 | 首次挂机判断失误 | 显示「首次执行，暂用默认估算」；样本积累后收敛 |
| R6 | 歌词接口为非官方接口，字段可能变更 | 歌词/翻译失效 | 解析层容错 + 降级为单语/无歌词，其他物料照常产出 |
| R7 | 模型输出语义搞反 | 主音和声互换，返工 | 实测「主音为领唱、和声为伴唱」并写进验收 |
| R8 | 误碰 `D:\Videos` 下其他项目文件 | 不可逆损失 | 访问范围仅限第 1.3 节；写入仅限交付物文件名 |
| R9 | Apple Music 曲目地区限制/下架 | 单曲失败 | 明确提示「地区不可用」，直接标记失败 |
| R10 | 翻译 API 限流/欠费 | 双语失败 | 降级为单语 + 提示具体原因 |

## 附录 A：模型输出语义映射（实现只按此表执行）

```
<曲名>.flac
   │  [pass1] melband_roformer_inst_v2
   ├──▶ Instrumental  ──▶  伴奏.wav
   └──▶ Vocals        ──▶  完整人声（工作目录中间件）
                              │  [pass2] mel_band_roformer_karaoke_aufr33_viperx_sdr_10.1956
                              ├──▶ Vocals       ──▶  主音.wav
                              └──▶ Instrumental ──▶  和声.wav
```

> 依据：现有目录中 `1_1_酒干倘卖无-苏芮_(Vocals)_(Instrumental).wav` 是对「pass1 的 Vocals」再做一次分离得到的 Instrumental，即和声轨。UVR 输出名 `Vocals/Instrumental` 是**模型语义**，业务语义以本表为准。
